# Responsive conversation and readable accounts — 0.4.1

> Historical 0.4.1 voice design: superseded by the 0.4.2 recovery described in `VOICE-RECOVERY.md`. The voice changes below were reverted after slower/broken speech was reported. The connected-identity section still describes the current implementation.

## Voice choice — reverted in 0.4.2

**Agent → Voice → KAI conversation · Fast** is now KAI's default. It uses an installed Android offline voice in the selected language, with a light 1.12 pitch and 1.02 rate multiplier. This is a different voice from Azelma; it preserves a little character without running the larger desktop model on every phrase. Preview and choose another voice in the same picker. Original **KAI Desktop · Azelma** remains bundled and selectable with its existing Cute KAI effect and native model unchanged.

A one-time encrypted-state migration changes KAI's previous Azelma default to Fast. Named Android voice selections and an explicit device-default selection survive. Other characters, credentials, speech settings, conversations, projects, memory and tasks are retained. Selecting Azelma again after the update survives subsequent restarts. No voice download or paid inference request is initiated by the update. If no downloaded voice supports the chosen language, KAI explains that speech is unavailable; choose another installed voice/language or download a voice in Android's text-to-speech settings. It does not silently select a network voice for Fast.

The previous desktop path performs CPU inference for a full phrase, applies the Cute KAI processing, then plays it. The next phrase previously waited for playback to finish. The model work, not just the pitch setting, is a likely contributor to phone delay. This update avoids that model for Fast. It does not make a measured physical-phone latency claim.

Platform speech can prepare one following phrase while the current one plays. The queue stays bounded at two phrases; the desktop model retains a single phrase. Only the playing phrase can advance the heard transcript, and range-start callbacks mark the start rather than the unheard end of a range. Stop, interruption, output changes, errors in either queued phrase and backgrounding flush the queue. Generation IDs reject stale callbacks from a previous reply.

The first phrase can start around 72 characters rather than 120, with an early partial flush after 240 ms and a minimum 24 characters. Complete short greetings can start sooner. Punctuation and Unicode boundaries are retained. Natural endpoint continuation is 700 ms, Quick 350 ms, and Patient 1900 ms; unfinished sentences still receive additional time. These waits are app settings, not end-to-end performance measurements. Recognition endpointing, the selected AI provider/model, networking and Android's TTS engine still affect conversational responsiveness.

This remains the foreground Android recognizer plus streaming text/TTS design. A dedicated duplex speech-to-speech backend and physical-phone acoustic tuning are future work, not part of this release.

## Connected identities

`alias` and `word_id` are Composio connection labels, not proof of a person's account. Connection cards no longer display these autogenerated strings or repeat the identity below the header. Toolkit titles include **YouTube**, **Google Drive**, **Google Docs** and **Google Sheets**.

KAI first uses Composio's documented `state.val.displayName` projection (rejecting values equal to the autogenerated alias). Gmail retains its existing verified, read-only `GMAIL_GET_PROFILE` path. Missing identities for these services can be enriched with fixed current-user profile reads:

| Services | Identity shown when available |
| --- | --- |
| Discord | Current user display name and @username; bot identities marked Bot |
| YouTube | Current channel title and @handle; ambiguous multiple-channel results are rejected |
| Google Drive | Current user's email or display name |
| Google Docs, Sheets, Calendar, Tasks, Meet, Photos | Verified Google email or profile name; Drive current-user fallback if granted |
| GitHub | Authenticated @login |
| Outlook, Outlook Calendar, OneDrive, Teams, SharePoint | Current Microsoft mail/user principal name or display name |
| Slack | Authenticated workspace and username |
| Spotify | Current display name or Spotify user ID |
| Other services | Provider-supplied display name, when present |

The profile allowlist is compiled into the app. The model cannot supply URLs, headers, OAuth tokens, alternate user IDs or arbitrary proxy bodies. Each read rechecks the exact account's owner, active status and toolkit. Requests include the exact connected-account ID and configured owner; Composio supplies provider authentication. Upstream status/error fields are checked even when the proxy transport returns HTTP 200. Only bounded, sanitized identity fields enter the cache/UI; raw provider profile/auth data is not saved.

Profile enrichment runs separately from account discovery and inference, with at most three concurrent reads and an eight-second per-account deadline. Successful identities are cached for 15 minutes and failures for one minute. Cancellation is not cached as failure. Credential changes, disconnects, newer refreshes and backgrounding invalidate pending display work. Cached labels never authorize actions: actions still reverify the exact account and existing approval bindings.

A provider may withhold a profile because of its scopes or account type. The app then shows **Connected account** with **Account details unavailable**, keeps the connection usable, and does not invent an email, expose a generated alias, or force a reconnect. Proxy access may need the Composio project's Proxy execute (Legacy): Write permission. These changes were tested with synthetic responses; the owner's live service scopes have not been tested.
